## 1. Stripe API — current state

### 1.1 v1 vs v2 events: snapshot vs thin

There are two delivery formats. The format is chosen when the **event destination** is
created, not by the API version of the resource alone.

- **Snapshot events** contain the complete `Event` object, including an
  eventually-consistent snapshot of the related resource, plus `previous_attributes`.
  They are **versioned by API version**, so the destination's pinned API version must
  match the SDK used to deserialize it (mismatched versions cause deserialization
  failures in statically typed SDKs). They are generated by both API v1 and API v2
  resource changes.
- **Thin events** contain a lightweight notification: the event `id`, `type`,
  `related_object` (`{id, type, url}`), `context`, and `reason`. They are **unversioned**,
  which is the key property: you can upgrade the SDK or API version without touching the
  destination configuration. The complete event is obtained with `fetchEvent()` and the
  latest resource state with `fetchRelatedObject()`.

Stripe's own guidance: **"For new integrations, use thin events."** Use snapshot events
only for a third-party tool that requires the complete `Event` object, or when you need
`previous_attributes` without an extra API call.

Thin notification shape (from the docs):

```json
{
  "id": "evt_test_65UIRNU7G1XbhCfOim416TgmEI4ASQ3jHxXt8RFwXoeVwO",
  "object": "v2.core.event",
  "type": "v2.core.account.updated",
  "livemode": false,
  "created": "2026-03-09T13:00:28.435Z",
  "context": null,
  "reason": { "type": "request", "request": { "id": "req_...", "idempotency_key": "ik_..." } },
  "related_object": { "id": "acct_1T93Q4Pmpb34Vto6", "type": "v2.core.account", "url": "/v2/core/accounts/acct_1T93Q4Pmpb34Vto6" }
}
```

**Decision for Tangerine.** The webhook ingestion layer (Phase 3) will be built around
the **thin-event** model: dedupe on the notification `id`, use `snapshot_event` when
present (interop events) as the idempotency key, and treat missing/extra fields
defensively. Because the notification payload is unversioned and stable, the shape we
persist will not need a migration on every Stripe API bump. For local/behavioral testing
we do not depend on live Stripe deliveries; we sign synthetic payloads with the same
HMAC scheme Stripe uses (see 1.3) so the production verification code path is exercised
exactly.

Source: <https://docs.stripe.com/events/how-events-work>,
<https://docs.stripe.com/event-destinations>,
<https://docs.stripe.com/events/set-up-events>

### 1.2 Idempotency key semantics — v1 vs v2

- **v1**: idempotent replay only for `POST`; replay window **24 hours**; on a repeat the
  API **always returns the previously saved response, even if it was an error**.
- **v2**: idempotent for all `POST` and `DELETE`; replay window **30 days**; a replay is
  scoped to the same API + account/sandbox. If the first attempt **failed or partially
  failed**, v2 **re-executes the failed portions and returns a new response** rather than
  replaying the error.

The `Idempotency-Key` header takes a client-generated unique value (a UUID is
recommended). If absent, Stripe generates one — but then you lose the retry guarantee, so
always send one.

**Implication.** Our own idempotency service (Phase 2) must model the v2 behavior, not
the v1 behavior: a `FAILED` key is retryable and should re-execute from its recovery
point, whereas a `COMPLETED` key must replay the stored response. This matches Brandur's
recovery-point model (§5) exactly.

Source: <https://docs.stripe.com/api-v2-overview>,
<https://stripe.com/blog/idempotency>

### 1.3 Webhook signature verification in Node.js

Two entry points depending on format:

- Snapshot / v1-style: `stripe.webhooks.constructEvent(rawBody, signatureHeader, endpointSecret)`.
- Thin / v2-style: `client.parseEventNotification(rawBody, signatureHeader, endpointSecret)`
  (returns a typed `EventNotification`).

Mechanics that matter:

- The `Stripe-Signature` header carries a timestamp (`t=`) and one or more signatures,
  each prefixed by a scheme (`v1`, plus a fake `v0` in test mode). HMAC-SHA256. **Ignore
  all schemes other than `v1`** to prevent downgrade attacks.
- The **raw request body is required**; any framework JSON parsing before verification
  breaks it. In Fastify/Nest this means capturing the raw body (register a content-type
  parser that keeps the buffer) and passing it through untouched.
- Default replay tolerance is **5 minutes** between the `t=` timestamp and now; it is
  configurable. Clock sync (NTP) matters.

**Decision.** Verify manually against our own tested verifier (`t` split, HMAC-SHA256
over `"{t}.{payload}"`, constant-time compare, configurable tolerance) so behavioral
tests can sign payloads deterministically and so a future Stripe SDK upgrade cannot
silently change our verification path. The verifier lives behind the same interface used
by a real Stripe SDK call, so swapping to `parseEventNotification` later is one adapter.

Source: <https://docs.stripe.com/webhooks?lang=node>,
<https://docs.stripe.com/webhooks>

## 2. PostgreSQL — deferred constraint triggers

PostgreSQL 18 supports `CREATE CONSTRAINT TRIGGER`. Key rules, verbatim from the docs:

- A constraint trigger **must be an `AFTER ROW` trigger on a plain table**.
- It "can be fired either at the end of the statement causing the triggering event, or at
  the end of the containing transaction; in the latter case they are said to be
  **deferred**."
- `DEFERRABLE INITIALLY DEFERRED` makes the trigger fire **at transaction commit**.
  `SET CONSTRAINTS { ALL | name } { DEFERRED | IMMEDIATE }` can force the timing within a
  transaction.
- "Constraint triggers are expected to **raise an exception** when the constraints they
  implement are violated." Enforcement *is* the trigger body.
- The `WHEN (...)` condition is evaluated **immediately**, not deferred. (So the condition
  must be decidable from the row at insert time; the balance check itself must be in the
  function body.)

Canonical usage the docs themselves show for a zero-sum invariant:

```sql
CREATE CONSTRAINT TRIGGER transfer_insert
  AFTER INSERT ON transfer
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW
  EXECUTE FUNCTION check_transfer_balances_to_zero();
```

Note the docs' older example uses `REFERENCING NEW TABLE ... FOR EACH STATEMENT` for a
non-constraint trigger; **constraint triggers cannot be statement-level**, so the
per-transaction zero-sum check must be implemented as a row-level function that queries
the aggregate for its `NEW."transactionId"` and raises if the sum is non-zero. Because
the trigger is deferred, all sibling postings of the transaction are visible by the time
it runs.

**Decision.** The ledger balance invariant (Phase 1) is a
`DEFERRABLE INITIALLY DEFERRED` constraint trigger on `LedgerPosting` that recomputes
`SUM(DEBIT) - SUM(CREDIT)` for the affected transaction and raises
`23514` (check_violation) / a custom `P0001` if non-zero. This is the single source of
truth for "postings balance," and it fires at commit — after the application has had the
chance to insert every leg.

Source: <https://www.postgresql.org/docs/current/sql-createtrigger.html>,
<https://www.postgresql.org/docs/current/sql-set-constraints.html>,
<https://www.postgresql.org/docs/current/sql-createtable.html>

## 3. Prisma — interactive transactions and row locking

- **Interactive transactions**: `prisma.$transaction(async (tx) => { ... }, options)`.
  `tx` is the transactional client; every call through `tx` is in the transaction.
  Options: `maxWait` (acquire, default 2000 ms), `timeout` (run budget, default
  5000 ms), `isolationLevel` (`ReadCommitted` default on PostgreSQL).
- **Raw queries inside a transaction** are supported: `tx.$queryRaw` for `SELECT`,
  `tx.$executeRaw` for mutations.
- **Pessimistic row locking** is expressed with raw SQL inside the transaction:

  ```ts
  const [row] = await tx.$queryRaw<Row[]>`
    SELECT id, status, "responseBody"
    FROM "IdempotencyKey"
    WHERE "userId" = ${userId} AND key = ${key}
    FOR UPDATE
  `;
  ```

  `FOR UPDATE SKIP LOCKED` is the pattern already used in this repo's outbox relay
  (`apps/api/src/outbox/outbox.service.ts`).

**Known gotcha (Prisma issue #17555):** a *batch* `$transaction([...])` containing a
**single** statement does **not** actually open a transaction, so a requested
`isolationLevel` is not applied. For the idempotency and ledger paths we always use the
**interactive** form when isolation matters, and we avoid relying on a single-element
batch.

**Decision.** Phase 2's concurrent-duplicate handling uses an interactive transaction
with `SELECT ... FOR UPDATE` on the idempotency row plus a lease (`lockedAt`) and a
unique `(userId, key)`. Phase 5's sweeper uses `FOR UPDATE SKIP LOCKED`, consistent with
the existing outbox relay.

Source: <https://www.prisma.io/docs/orm/prisma-client/queries/transactions>,
<https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/raw-queries>,
<https://github.com/prisma/prisma/issues/17555>

## 4. Saga pattern — orchestration with compensations

Verified against Temporal's design-patterns documentation (with side-by-side SDK samples),
the original AWS/"Reference 6: A Saga on Sagas" material, and current TypeScript
implementations.

Consensus rules that we adopt:

1. **Compensate in LIFO order.** Register a compensation as each forward step completes;
   on failure, run them in reverse order of completion.
2. **Compensations must be idempotent.** They may run when the forward action never
   completed (if registered before execution) or more than once after a crash mid-rollback.
   Use an idempotency key per compensation.
3. **Register compensation *before* the forward action executes** when the forward action
   has side effects that may occur before it returns (e.g. a charge that succeeds but whose
   response is lost). The compensation must then tolerate "nothing to undo."
4. **A failed compensation is terminal for automatic control flow** — it must be surfaced
   for manual intervention, because the runtime cannot prove whether the side effect
   occurred. Persist compensation state for recovery.
5. Orchestration (a central coordinator with explicit step table) is preferred over
   choreography when steps must be sequenced and reasoned about; this is the AWS
   Prescriptive Guidance position and fits our checkout flow.

**Decision.** Phase 4 implements a **hand-rolled orchestrator** (not a library): a
persisted `SagaState` row with `completedSteps`/`compensationsRun` JSONB arrays, an
ordered step table where each step declares `forward` and `compensate`, and LIFO
compensation on failure. Rationale: the orchestration surface is small and the
persistence requirements (crash recovery, failure injection for tests) are specific
enough that a general-purpose library adds a dependency without removing much code. The
step table is data-driven so the same machine can serve future saga types.

Source: <https://docs.temporal.io/design-patterns/saga-pattern>,
<https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga.html>
(via AWS Samples saga pattern), <https://github.com/temporalio/samples-typescript/tree/main/saga>

## 5. Idempotency with recovery points (Stripe / Rocket Rides)

Brandur Leach's design (Stripe) is the reference model:

- **Atomic phase**: a set of local DB mutations between two *foreign* state mutations,
  made atomic by the database.
- **Recovery point**: a label written (in the same transaction as the phase) after each
  phase completes. A retry jumps back to the point just before the last failure.
  Initially `started`; `finished` once a definitive response exists.
- The key row stores the request signature (`request_params`) and, on completion, the
  stored response (`response_code`, `response_body`); a retry with the same key but
  **different** params is a `409` (client bug).
- **Lease / lock**: `locked_at` with `IDEMPOTENCY_KEY_LOCK_TIMEOUT` prevents two in-flight
  attempts. A stale lock (older than the timeout) may be re-acquired by a retry.
- A **reaper** deletes keys after a retention window (Stripe: 24h v1 / 30d v2).

There is no IETF RFC yet; the `httpapi` WG draft for `Idempotency-Key` is still a draft,
so we follow the de-facto Stripe semantics.

**Decision.** `IdempotencyKey` stores `(userId, key, requestHash, status, recoveryPoint,
responseStatus, responseBody, lockedAt, expiresAt)`, unique on `(userId, key)`.
`execute()` upserts-and-locks, runs the caller's function passing a `recoveryPoint`
callback, records the response on success, and preserves the recovery point on failure so
a retry can resume (v2-style) rather than replay a stale error.

Source: <https://brandur.org/idempotency-keys>,
<https://github.com/brandur/rocket-rides-atomic>,
<https://stripe.com/blog/idempotency>

## 6. Ledger design notes (informs Phase 1)

- **Append-only** is the whole point: no `UPDATE`, no `DELETE`. Enforced by a
  `BEFORE UPDATE OR DELETE` trigger that raises, *plus* `REVOKE UPDATE, DELETE` as defense
  in depth. Note: revoked privileges do **not** stop the table **owner** (our dev role
  `tangerine` owns the schema), and a superuser bypasses them entirely — so the **trigger
  is the real guarantee** and the revoke is a second layer.
- **Balances are derived**, never stored: `SUM(credit) - SUM(debit)` grouped by account.
  A stored balance is a cache that can drift; an aggregate against an append-only table
  cannot.
- **Hash chain for tamper detection**: each transaction stores `previousHash` and
  `hash = SHA256(canonical(seq, kind, sourceType, sourceId, createdAt, postings, previousHash))`.
  A global monotonic `seq` plus a transaction-scoped advisory lock serialises chain
  extension so the chain is unbroken under concurrency. `verifyIntegrity()` walks the chain
  in `seq` order and recomputes.

```

herdr pane wait-output <pane_id> (--match TEXT | --regex PATTERN) [--timeout MS]
herdr pane split [<pane_id>|--current] --direction right|down [--cwd PATH] [--no-focus]
herdr agent start <name> --kind KIND --pane ID
herdr agent prompt <target> <text> [--wait] [--until STATUS] [--timeout MS]
herdr agent wait <target> [--until STATUS] [--timeout MS]
herdr agent read <target> [--source ...] [--lines N]
herdr notification show <title> [--body TEXT] [--position ...] [--sound none|done|request]
```

Notes that shaped the orchestration:

- `herdr tab create` returns `.result.tab` and `.result.root_pane`; the pane id
  (e.g. `w13:p2`) is the handle for `pane run` / `pane read`.
- `agent wait` is the Herdr-native replacement for `sleep`/`timeout`; states are
  `idle | working | blocked | done | unknown`. `--until` is for a specific state; without
  it, wait settles on the first `idle|done|blocked`.
- `worktree create` produced a linked worktree at
  `/home/harsha/.herdr/worktrees/tangerine/feature-marketplace-payments`, opened it as
  workspace `w13`, and grouped it with the parent `tangerine` workspace.
- This agent runs inside Herdr (`HERDR_ENV=1`, workspace `w0`), which is the precondition
  the skill requires before issuing control commands.

## 9. Open questions / uncertainties

- **Thin events for API v1 resources** were in private preview at time of writing; we
  target the v2 thin model and keep the ingestion shape stable, so a change in preview
  surface does not affect persisted rows.
- **`parseEventNotification` ergonomics** differ across SDK majors; we isolate
  verification behind one adapter (§1.3) to absorb that.
- **Advisory-lock throughput for the ledger hash chain.** Serialising chain extension
  caps ledger write concurrency at one writer at a time. For the demo volumes here this is
  irrelevant (microsecond critical sections), and correctness of the chain wins. If it ever
  matters, the chain can be sharded per account with a `(accountId, seq)` key.
